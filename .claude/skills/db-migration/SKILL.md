# Безопасная миграция PostgreSQL

Миграции живут в `migrations/` (goose) и применяются по порядку. Опасные миграции без подтверждения пользователя не применяются никогда.

## Перед написанием

- [ ] Сформулируй, зачем изменение и какие запросы в `queries/` оно затронет.
- [ ] Классифицируй риск:
  - **безопасно**: новая таблица, новая nullable-колонка, новый индекс;
  - **опасно**: удаление или переименование таблиц и колонок, смена типа, NOT NULL на заполненной таблице, массовое изменение данных.
- [ ] Опасная миграция — сначала объясни пользователю последствия и получи согласие.

## Написание

- У каждой миграции есть рабочий **down**. Если откат теряет данные, так и напиши в комментарии.
- Одна миграция — одно логическое изменение.
- Внешние ключи и `CHECK` — для целостности. Индексы — под реальные запросы, не «на всякий случай».
- Изменение структуры и перенос данных — отдельными миграциями.
- Существующую, уже применённую миграцию не редактируй. Пиши новую.

## Проверка

- [ ] Перед опасной миграцией — резервная копия `pg_dump`. Путь к ней сообщи пользователю.
- [ ] Цикл up → down → up проходит на тестовой БД.
- [ ] Перегенерирован код sqlc, проходят тесты пакетов с затронутыми запросами.
- [ ] На реальной БД миграцию применяет пользователь или ты по его явной просьбе.
